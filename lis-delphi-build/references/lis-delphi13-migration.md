# Переход ЛИС (medicalgenomics) с Delphi 10.3 на RAD Studio 13.x

Карта работ и ловушек перехода большого VCL-проекта (9 000+ `.pas`, 4 400 `.dfm`) на новую версию
RAD Studio с сохранением сборки на старой. Состояние — проверять заново, конкретика ниже полезна как
скелет и как список уже пройденных грабель.

## Две версии одновременно — правило

- **Прод-стек: Delphi 10.3 Rio = `Studio\20.0`, компилятор 33.0.** Вся проверка «работает» — только этой сборкой.
- **Целевой стек: RAD Studio 13.x** — на машинах рядом (`BDS\37.0` в реестре, `Studio\37.0\bin`).
  Сборка на 37.0 самого прод-кода ничего не доказывает: она уже прошла, а в МГ нужна 10.3.
- Ветка/правки под 13 держать в **отдельной ветке репозитория**, а не в резервной копии каталога: иначе
  следующий чистый клон их теряет.

## Компоненты: отдельные репозитории + субмодули

Сторонние библиотеки вынесены из дерева проекта в свои git-репозитории и подключены субмодулями в `lib/`:

```
medicalgenomics
├── lib/devexpress    (DevExpress VCL, cx*/dx*)
├── lib/fastreport     (FastReport 6 VCL Enterprise)
├── lib/ehlib          (EhLib)
├── lib/ems-export     (EMS Advanced Data Export)
├── lib/ems-import     (EMS Advanced Data Import)
├── lib/graphics32     (GR32)
└── Registr/registr.dproj
build-config           (CI-конфиг, НЕ субмодуль: клонируется в build/)
```

- Компоненты собираются **из своих каталогов** скриптом `build-component.ps1` (по одному в каждом репо),
  а оркестратор `build-orchestrator.ps1 -Target all` идёт в порядке:
  `devexpress → ehlib → fastreport → ems-export → ems-import → graphics32 → проект`.
- Сборка каждого компонента **атомарная**: пишет в `out.tmp/`, при полном успехе заменяет `out/`. При ошибке
  старый `out/` не тронут — важно, иначе полупустой набор DCU ломает последующие компоненты.
- Состав пакетов — манифестом, а не «всё, что есть»:
  * DevExpress — `packages.txt` (порядок Required→Optional, генерится из `DevExpress.yaml`), флаги как у
    DxAutoInstaller (`--no-config -A<алиасы> -NS<неймспейсы> -DUSENATIVELOOKANDFEELASDEFAULT`),
    пакеты без `.dpk` (dxEMF, dxReports, dxDashboards) и BDE — пропускать;
  * FastReport — 43 пакета `*37.dpk`, **многопроходно** (зависимости разрешаются повторными проходами);
  * EhLib — `msbuild` по `.dproj` из `RADSpecific/RADStudioXE13`; BDE-пакет пропускать;
  * EMS export/import — `msbuild` по 2 `.dproj` из `packages/RADStudioXE13`;
  * GR32 — `msbuild GR32_R.dproj` (только runtime).
- `dx.exe` (CLI DxAutoInstaller) для нашего набора не годится — компилировать `dcc32` по манифесту.
- `.res/.dfm/.dcr` компонентов копировать **рядом с DCU** в `out/dcu`, иначе на проекте `E1026 File not found: *.res`.

## Регистрация пакетов в IDE (без инсталлятора)

- `HKCU\Software\Embarcadero\BDS\37.0\Known Packages` — по строке на пакет; готовить как `.reg`-шаблон
  в `build-config/reg/`, подстановка `<PROJECT_DIR>` делается скриптом (`.reg` переменных не понимает).
- Design-пакеты грузят свои runtime-BPL по **PATH** IDE — добавить туда каталог с BPL (`LibD37`), иначе
  «пакет установлен, а компоненты не появляются».
- Скомпилированные BPL кладутся в `C:\Users\Public\Documents\Embarcadero\Studio\<ver>\Bpl`.
- Правки реестра применять на каждой сборочной машине отдельно: на build-сервере реестр другой.

## Типовые блокеры (в порядке появления)

| Симптом | Причина | Лечение |
|---|---|---|
| `Unit not found` при сборке проекта | в `DCC_UsePackage`/`uses` есть `dx*`, `frx*`, `QExport*`, `EhLib*`, `GR32*`, а library path не указывает на них | прописать `DCC_UnitSearchPath` на `lib/<name>/out/dcu` (в `.dproj` относительными путями) + импорт `components-library-path.reg` с подстановкой корня воркспейса |
| `E1026 File not found: *.res` | `.res/.dfm` компонента остались в исходниках, а DCU в `out` | копировать ресурсы рядом с DCU на этапе сборки компонента |
| `E2003 Undeclared identifier: 'NULL'` в `QExport4CustomSource.pas` | в library path попал каталог `source` EMS, и компилятор пересобирает исходник вместо готового DCU (условный `uses Variants`) | исключить `EMS …\source` из путей, использовать готовые DCU |
| `E2003`/`E1026` по языковым ресурсам EhLib | после переименования проекта пакетам не досталось `.res` со своим именем; нет пути к `LangResources\Res` (21 языковой `.dfm`) | вернуть `.res` по именам пакетов, прописать `LangResources\Res` |
| `F2051 Unit Vcl.Graphics compiled with a different version` | в проект попал юнит, собранный другим компилятором (смешение 10.3/13) | убрать чужой DCU/юнит из обоих проектов, пересобрать начисто |
| `fs_iinterpreter not found` | два разных канала сборки (msbuild vs dcc32-манифест) дают разные пути к пакетам FR | собирать компоненты только оркестратором, не смешивать способы |

## Проверка перехода

1. `build-orchestrator.ps1 -Target all` на **чистой** сборочной машине — компоненты должны собраться из
   субмодулей, без заранее разложенных артефактов. Это и есть доказательство воспроизводимости.
2. Сборка проекта 10.3 (`Stud io\20.0`) — прод-путь не сломан.
3. Сборка проекта 13.x — целевой путь.
4. Обе ветки собираются из одного дерева; матрица версий компонентов (какая версия DevExpress/FR/EMS/EhLib
   официально держит 13.x) — отдельный артефакт, без неё «собралось» не равно «поддерживается».

## Сборочная машина (WINBUILD)

- VM на pve, Windows Server, RAD Studio 10.3 + 13.x установлены рядом, Jenkins-агент (`D:\jenkins`).
- Типовое состояние «после установки»: **IDE есть, компонентов нет** — каталогов `C:\COMPONENTS`,
  `D:\COMPONENTS`, `H:\COMPONENTS` нет, BPL в `Public Documents` нет. Сквозная сборка падает на первом
  компоненте, пока не прогнан оркестратор.
- Проверять состав машины до обещаний: `Test-Path` по каталогам компонентов, число BPL, версия `dcc32`.
