# Версионирование инфраструктуры в git

Триггер: BOSS говорит «всё в гит», «версии нам нужны» или просит положить рукотворные артефакты в репозиторий.
Смысл — не разовая заливка, а чтобы изменения дальше копились в истории САМИ.

## Раскладка репозиториев

- Один репозиторий на класс работ, а не мешанина: система сборки образов отдельно, скрипты/настройки агента отдельно.
- Что версионировать: скрипты, шаблоны, манифесты, определения задач, инструкции агентов,
  карточки источников документации (`SOURCE.md` — без самих гигабайтов первоисточников).
- Что НЕ версионировать: бинарные инсталляторы и колёса (их адреса есть в манифесте), готовые ISO,
  сгенерированные из шаблонов файлы (они собираются подстановкой секретов на месте), ключи и пароли.
- **Исключение — прошивки железа (BIOS/UEFI).** Их храним: артефакт невоспроизводим (вендор может снять
  версию с сайта), а знать, чем прошита плата и что в этой версии, нужно. Раскладка — `firmware/<вендор>-<плата>/`
  внутри `hermes-infra`: официальный архив вендора, распакованный файл прошивки, `README.md` (версия и что
  внутри — например версия AGESA, дата выпуска, источник, порядок прошивки, заметки по настройке) и
  `SHA256SUMS`. Цена — десятки мегабайт в истории; если репозиторий должен остаться лёгким, держать только
  архив и суммы, а распакованный файл не хранить.

## Импорт существующей кодовой базы как AS-IS снапшот

Класс поручений: «залить в git все исходники из рабочей папки; в папках куча мусора — мусор не заливать; пометить,
что это то, что есть сейчас (в будущем переработка)».
- Отбор по типам: ВКЛ — исходный код, формы/проекты, скрипты (sql и пр.), отчёты и их шаблоны (FastReport `.fr3`…),
  локализации, полезные конфиги. ИСКЛ — `.hg`/`.git` целиком (живой рабочий репозиторий источника не трогать и не
  заливать), архивы VCS, артефакты сборки (`.exe/.dll/.dcu/.bpl/.obj`…), кэши/бэкапы (`__history`, `__recovery`,
  `~*`, `*.bak`), медиа-мусор. `.hgignore` проекта — готовая основа для `.gitignore`.
- README в корне фиксирует состояние: «Снапшот AS-IS <дата>; проект черновой, планируется переработка» + краткий
  инвентарь (что вошло / что исключено); спорные файлы — включать и перечислять в отчёте.
- Источник — только чтение (рабочая машина BOSSа): файлы забирать по SMB (`C$`/`H$` доменной учёткой), git-операции
  локально, push в Forgejo. После заливки занести репу в OpenViking (`viking_add_resource`) с той же пометкой.
- Сторонние коммерческие компоненты и их дистрибутивы (DevExpress, EMS, EhLib, архивы с торрентов и т.п.) в репу
  НЕ заливать — лицензионные риски; исключение фиксировать в инвентаре. Если в проекте есть ПДн — репозиторий строго
  приватный, предупредить BOSSа в отчёте.

## Секреты: гейт перед коммитом (обязателен)

- **Скан по ЗНАЧЕНИЯМ, а не только по шаблонам.** Забрать все значения из `pass` (записи, строки без пробелов)
  и искать их подстрокой во всех текстовых файлах. Регулярки «password=…» ловят ложные срабатывания (токены
  архитектуры в unattend, имена драйверов) и пропускают реальные пароли.
- Если скан что-то нашёл — **коммит не делается вообще** (exit != 0), печатается файл и запись `pass`.
  Правило живёт в самом скрипте синхронизации, а не в голове агента.
- **Сгенерированные файлы с секретами заменить шаблонами** с плейсхолдерами (`{{SVC_JOIN_PW}}`, `{{VLAS_LOCAL_PW}}`):
  версионируется шаблон, а настоящие значения подставляются при сборке. Сгенерированный файл — в `.gitignore`.
- Значения из `pass` в ответах и логах не печатать (маскировать), секреты живут в Vaultwarden + pass,
  см. скилл `password-vault`.

## Публикация в Forgejo (<домен из окружения>)

```bash
TOK=$(pass show forgejo/boss-token)        # админский токен BOSS: сам создаёт репозитории
curl -s -X POST https://<домен из окружения>/api/v1/user/repos \
  -H "Authorization: token $TOK" -H 'Content-Type: application/json' \
  -d '{"name":"<repo>","description":"...","private":false,"auto_init":false,"default_branch":"main"}'
```

- Пушить по HTTPS с токеном (хранилище учётных данных — файл 600): это работает сразу.
  **Токен не должен попасть в `.git/config`** — remote задавать без токена, секрет отдавать helper'у.
- Публичный SSH-ключ можно зарегистрировать (`POST /api/v1/user/keys`), но не строить на нём сразу: пока ключ не
  разошёлся, `ssh -T git@…` отдаёт `Permission denied (publickey,password)`. Для автоматики брать HTTPS+токен.
- Токена нет под рукой — посмотреть `pass ls | grep -i forgejo` (там и админский токен, и учётка).

## Автосинхронизация (чтобы версии копились сами)

- Один скрипт: разложить живые исходники в дерево репозитория → скан секретов → `git add -A` → коммит → push.
  Пустой `git status` — выйти молча, коммит с меткой времени и понятным описанием класса правок.
- **`rsync --delete` стирает файлы, которых нет в источнике** — и первым делом `.gitignore` и `README.md`
  самого репозитория. Без `.gitignore` в коммит сразу уезжают сгенерированные файлы с секретами.
  Обязательные исключения при любом способе синхронизации: `--exclude .gitignore --exclude README.md`.
- Фоновая задача, запущенная в оболочке инструмента, умирает вместе с вызовом — для регулярной синхронизации нужен
  cron (Hermes `cronjob_manage`) или systemd-таймер, а не `nohup ... &` внутри шага.
- Идентичность коммитов задать явно (`git config user.name/email`), иначе на чистой машине коммит падает.
- **Каждая git-команда в скрипте синхронизации идёт с явным рабочим каталогом.** `git remote add origin …`,
  выполненный без `cwd=<репозиторий>`, уходит в каталог родителя и молча не применяется — следующий `git push`
  отвечает `fatal: 'origin' does not appear to be a git repository`. На нескольких репозиториях это легко
  пропустить, поэтому после настройки remote проверять `git remote -v`.
- **Под кроном без агента (`no_agent`) скрипт печатает только события.** Строка «без изменений» на каждом прогоне
  превращается в сообщение каждые N минут: выводить что-либо лишь когда были коммиты или ошибки.
- Коммит-сообщение — про КЛАСС изменения (одна строка); историю не засорять «update» без смысла.

## Проверка

- Что доехало: `git log --oneline | head` и `git ls-files | wc -l` локально; авторитетно — API Forgejo
  (`/api/v1/repos/<owner>/<repo>` → размер/ветка).
- **Факт доставки читать с сервера, а не из локального `git log`.** После ручного push запросить содержимое
  каталога: `/api/v1/repos/<owner>/<repo>/contents/<путь>` — вернёт имена, размеры и sha последнего коммита;
  у публичных репозиториев работает без токена. Ссылка для выдачи файла человеку — raw
  `https://<хост>/<owner>/<repo>/raw/branch/<ветка>/<путь>`.
- **Ручной коммит — с явными путями** (`git add -A firmware README.md`): в том же дереве по расписанию работает
  автосинхронизация, и незатейливый `git add -A` утащит в коммит её промежуточные файлы. После коммита с
  бинарниками проверять не только диапазон в выводе `git push`, но и наличие/размеры файлов через API.
- После настройки автосинхронизации прогнать её руками дважды: первый прогон коммитит, второй должен молчать.
